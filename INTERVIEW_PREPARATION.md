# Technical Interview Preparation Guide

This document provides clear, technically precise, interview-ready answers to the core AI Engineering Intern assignment questions.

---

### 1. What is RAG?
**Answer:**
Retrieval-Augmented Generation (RAG) is an architectural pattern that enhances Large Language Models (LLMs) by dynamically retrieving relevant external documents from a vector database and injecting them as context into the LLM prompt. This grounds the LLM's responses in domain-specific, authoritative data rather than relying solely on frozen parametric memory.

---

### 2. Why did you use RAG?
**Answer:**
LLMs are prone to hallucination, lack access to private/internal documents, and cannot update their knowledge dynamically without expensive re-training or fine-tuning. RAG provides a modular, low-cost, and verifiable approach that forces the LLM to answer using explicitly retrieved context with page-level citations.

---

### 3. Why ChromaDB?
**Answer:**
ChromaDB is an open-source, Python-native vector database that supports persistent local storage (`./chroma_db`), fast approximate nearest neighbor (ANN) vector search (HNSW), and rich metadata filtering (`source`, `page`, `chunk_id`). It allows running and evaluating the complete RAG pipeline locally without external cloud dependencies or API keys.

---

### 4. Why not Pinecone?
**Answer:**
The assignment explicitly allowed selecting any vector database. While Pinecone is a fully managed cloud service ideal for massive distributed production deployments, ChromaDB allowed keeping the project 100% self-contained, reproducible, and easy to run locally. The RAG architecture itself is database-agnostic; swapping ChromaDB for Pinecone only requires updating the vector store adapter layer.

---

### 5. What are embeddings?
**Answer:**
Embeddings are high-dimensional dense vector representations of text generated by neural networks (e.g., Transformers). They capture semantic meaning, context, and concept similarity in a continuous vector space, allowing mathematically comparing text snippets based on meaning rather than literal keyword matching.

---

### 6. How does semantic search work?
**Answer:**
1. A user query string is passed through the embedding model to produce a query vector $\vec{q}$.
2. The vector database computes distance metrics (such as Cosine distance or Dot product) between $\vec{q}$ and stored document vectors $\{\vec{d}_i\}$.
3. The database ranks and returns the top-$K$ nearest vectors along with their corresponding text content and metadata.

---

### 7. Why did you choose this embedding model?
**Answer:**
I selected `sentence-transformers/all-MiniLM-L6-v2`. It maps sentences into a 384-dimensional dense vector space and offers an optimal balance of fast inference speed, low memory usage, zero cost, and high performance on semantic similarity tasks, making it ideal for local development and technical evaluation.

---

### 8. How does ChromaDB work under the hood?
**Answer:**
ChromaDB uses SQLite for metadata and document storage, combined with HNSW (Hierarchical Navigable Small World) graph indexes for fast approximate vector search. In persistent mode, it saves index data structures to disk (`./chroma_db`), allowing vectors to persist across application restarts.

---

### 9. What is LangGraph?
**Answer:**
LangGraph is a framework by LangChain for building stateful, multi-actor, cyclic applications using formal state graph abstractions. It represents workflows as nodes (functions) and edges (control flow logic), enabling fine-grained control over execution steps, conditional routing, and state persistence.

---

### 10. Why LangGraph instead of a simple LangChain chain?
**Answer:**
A standard LangChain `LLMChain` is linear and struggles with conditional decisions. LangGraph allows explicit state management (`RAGState`), node decomposition (`retrieve` $\to$ `evaluate` $\to$ `generate` or `refusal`), and deterministic conditional routing based on vector retrieval scores before calling the LLM.

---

### 11. Explain your LangGraph state structure.
**Answer:**
The `RAGState` is a `TypedDict` containing:
- `question` (str): The user query.
- `retrieved_documents` (list): Top-k chunks returned from ChromaDB.
- `context` (str): Combined text block with page headers.
- `retrieval_scores` (list): Cosine distance scores.
- `confidence` (float): Normalized retrieval confidence score ($0.0 - 1.0$).
- `is_relevant` (bool): Boolean flag comparing confidence against `RELEVANCE_THRESHOLD`.
- `answer` (str): Grounded answer or refusal message.

---

### 12. Explain each LangGraph node in your workflow.
**Answer:**
1. `retrieve_documents`: Queries ChromaDB and populates retrieved chunks, context, scores, and confidence.
2. `evaluate_relevance`: Compares `confidence` against `RELEVANCE_THRESHOLD` (0.50).
3. `generate_answer`: Invokes the LLM using context and strict system prompts if relevant.
4. `format_refusal`: Returns the strict refusal string if irrelevant.
5. `format_response`: Passes final state to response output.

---

### 13. How does retrieval work in your pipeline?
**Answer:**
The user question is embedded using `EmbeddingService.embed_query()`. The resulting 384-dimensional vector is queried against ChromaDB using `collection.query()`. The top 5 document chunks, their metadata (page, source), and raw cosine distances are extracted.

---

### 14. What is top-k?
**Answer:**
`top_k` specifies the maximum number of most similar document chunks to retrieve from the vector database for a given query. I selected `TOP_K=5` to provide sufficient context coverage without exceeding token limits or cluttering the LLM context.

---

### 15. How did you select the chunk size?
**Answer:**
I chose a chunk size of `1000` characters (~150-200 words). This size is large enough to contain complete semantic concepts, paragraphs, and facts while remaining fine-grained enough to avoid mixing unrelated topics.

---

### 16. Why use chunk overlap?
**Answer:**
I set `chunk_overlap=150` characters. Overlap ensures that key sentences or facts spanning boundary split points are not cut in half, maintaining contextual continuity across adjacent chunks.

---

### 17. How do you prevent hallucination?
**Answer:**
1. **Confidence Thresholding**: LangGraph routes irrelevant queries to a grounded refusal without calling the LLM.
2. **Strict System Prompt**: Instructs the LLM to rely ONLY on facts present in the context.
3. **Zero Temperature**: `temperature=0.0` prevents creative sampling.
4. **Source Attribution**: Forces context citations (`[Page N]`).

---

### 18. How do you determine whether retrieved context is relevant?
**Answer:**
Relevance is determined by comparing the mathematical `retrieval_confidence` score against `RELEVANCE_THRESHOLD` (0.50). If confidence is below 0.50, the context is classified as irrelevant.

---

### 19. How is retrieval confidence calculated?
**Answer:**
ChromaDB returns Cosine Distance $d \in [0.0, 2.0]$. Cosine Similarity $S = 1.0 - d_{\text{min}}$.
$$\text{Confidence} = \max(0.0, 1.0 - d_{\text{min}})$$
This converts raw vector distances into a transparent $0.0 - 1.0$ confidence metric.

---

### 20. Why shouldn't an LLM-generated confidence score be trusted directly?
**Answer:**
LLMs are non-calibrated generative models prone to overconfidence and sycophancy. Asking an LLM "How confident are you from 1 to 10?" yields arbitrary, non-deterministic scores. Deriving confidence mathematically from vector space distance provides an objective, reproducible metric.

---

### 21. How does FastAPI expose the RAG system?
**Answer:**
FastAPI exposes two main endpoints:
- `GET /health`: Returns service health and ChromaDB chunk count.
- `POST /chat`: Accepts `ChatRequest({"question": "..."})`, validates input via Pydantic, executes `RAGGraphWorkflow.run()`, and returns `ChatResponse` with answer, confidence score, and chunk metadata.

---

### 22. How would you scale this application for production?
**Answer:**
1. **Vector DB**: Migrate ChromaDB to a distributed vector store like Pinecone, Qdrant, or Milvus.
2. **API Layer**: Deploy FastAPI on Kubernetes behind an Application Load Balancer (ALB).
3. **Caching**: Cache frequent query embeddings and responses in Redis.
4. **Async Processing**: Use background workers (Celery/Temporal) for heavy document ingestion pipelines.

---

### 23. How would you improve retrieval quality?
**Answer:**
1. **Hybrid Search**: Combine BM25 keyword search with vector dense retrieval using Reciprocal Rank Fusion (RRF).
2. **Reranking**: Use a cross-encoder model (`bge-reranker-large`) to re-rank top-20 retrieved chunks down to top-5.
3. **Query Expansion**: Generate 3-5 variations of the user question to capture broader context.

---

### 24. What is hybrid search?
**Answer:**
Hybrid search combines sparse lexical search (like BM25, which matches exact keywords, serial numbers, and acronyms) with dense vector search (which captures semantic meaning). Combining both yields superior recall and precision.

---

### 25. What is reranking?
**Answer:**
Reranking is a two-stage retrieval process. Stage 1 uses fast vector search to retrieve a candidate pool (e.g., top-30 chunks). Stage 2 uses a heavier Cross-Encoder model to score each (query, chunk) pair directly, returning the top-5 most accurate chunks to the LLM.

---

### 26. What happens if ChromaDB is unavailable?
**Answer:**
The FastAPI route catches vector database exceptions and returns an HTTP 503 Service Unavailable status code with a clean error message, preventing application crashes and hiding stack traces from the user.

---

### 27. What happens if the LLM API fails?
**Answer:**
The `LLMGenerator` class includes error handling that catches API errors (rate limits, network timeouts) and falls back to a deterministic local extract or refusal response, maintaining high service availability.

---

### 28. How would you evaluate this RAG system?
**Answer:**
I would build an evaluation benchmark dataset of 50+ question-answer pairs and use **RAGAS** (RAG Assessment) framework to measure:
- **Faithfulness**: Is the answer grounded in context?
- **Answer Relevance**: Does the answer directly address the question?
- **Context Recall**: Did retrieval fetch all necessary facts?
- **Context Precision**: How noise-free was the retrieved context?

---

### 30. What challenges did you face while building the project?
**Answer:**
1. **PDF Formatting Artifacts**: Raw PDF extraction can include weird characters and broken lines. I implemented custom regex text cleaning in `PDFLoader`.
2. **Grounding & Out-of-Scope Detection**: Out-of-scope questions originally returned weak nearest-neighbor chunks. I solved this by calibrating cosine similarity metrics into a transparent retrieval confidence score and routing low-confidence queries to a grounded refusal in LangGraph.
